Capabilities and status

CUDA-Q Logical reports its own status the way it reports evidence: three-way, and only against executable artifacts. A capability is shipped when it is part of the installed cudaq.logical package, and exercised only when a shipped test or example executes it — the lit/FileCheck suites and the pytest suite (which runs every Python example under preview/logical/examples/) are the evidence. A capability that is neither is out of scope: a deliberate boundary, stated here. Execution limitations and the information omitted during lowering are listed below.

What the product is

CUDA-Q Logical is a compiler and resource-estimation toolkit for fault-tolerant quantum computing. A program is refined through four strict semantic stages — P0 unplaced logical, P1 placed logical, P2 QEC realization, and P3 physical event graph and schedule. The estimation ladder has four tiers: Tier.LOGICAL, Tier.STATIC, Tier.ANALYTICAL, and Tier.SCHEDULE. Stim circuit text is an interchange emission target from a verified P2 gadget. Supported P3 physical builds also translate to Quake for execution through ordinary cudaq.run.

Present but not yet exercised

These APIs exist in the package but carry no executed test or example in this release, so the documentation does not teach them yet: dynamic codes (MeasurementPhase, EncodingEpoch), code switching (PatchTransform), concatenation (cudaq.logical.codes.Concatenated), meta-checks (cudaq.logical.codes.MetaChecks), and P2 block requests (cudaq.logical.codes.qec_block). Treat them as preview surface: use them at your own risk until exercised evidence lands.

Execution and documented boundaries

Execution uses ordinary CUDA-Q targets. cudaq.run(physical_build, ...) translates a supported P3 Build through Build.to_quake() and executes the resulting circuit on the selected target. A program can return a bool, a list of bool, or a tuple of bool. Each shot returns a bool for a single entry, and a list[bool] in return order for several. No implicit final measurements or decoding are added. See the Steane Bernstein–Vazirani and T-factory execution examples.

Execution covers a subset of P3. Forms such as resource and factory flows, in-graph postselection, bounded retry, code epoch changes, and patch-granularity resources produce diagnostics instead of executable Quake. Support for compiling or estimating these forms does not imply execution support.

Target capabilities and memory limits still apply. CUDA-Q’s stim target executes Clifford circuits with supported Pauli noise. Non-Clifford examples, and any Pauli-product rotation, require a compatible target, such as nvidia or density-matrix-cpu. Successful compilation does not guarantee that a simulator has enough memory for the physical carriers, including ancillas. The ordinary noise_model argument applies supported channels to emitted gates. P3 operating-point error and timing assumptions remain estimation inputs, not runtime noise channels.

Execution does not model the physical schedule. The current lowering omits phys.delay, phys.barrier, phys.move, and event.fence. It does not execute their timing, transport, or synchronization effects or model the associated idle and transport noise. It does not submit P3 schedules to hardware.

Annotated Stim export covers closed single-block contract chains. The Python exporter lowers detector and observable declarations and attaches an explicit physical noise policy. See the surface-memory example. Sampling, DEM extraction, and decoding use downstream tools. P3 physical error and timing assumptions remain inputs to resource estimates; they do not select the circuit’s noise policy.

Native gadget EDEM derivation and serial composition are also available; see Derive an error model from gadgets.

Stages stop at P3. P3 represents physical carriers, routing, native events, and schedules. Quake translation connects supported physical graphs to CUDA-Q’s existing execution path and simulators without adding a Logical compilation stage.

The native P1 placer is a subset. qlx-to-lvm is a deterministic first-fit placement for explicitly machine-scoped, inlined programs; the Python placement solver (cudaq.logical.compiler.place) is the rich path. The native pass fails on inputs outside the shared supported subset rather than approximating.

Stim emission is terminal and checked. The --fabric-to-stim translation accepts a verified P2 entry gadget. Emission never invents an implementation that selection did not link.

Rotation synthesis is explicit, not automatic. cudaq.logical.compiler.synthesize legalizes a logical program to a named gate set (Clifford+T, example 01) under an operator-norm precision= bound; unsupported gate sets are rejected with a ValueError rather than approximated.

Paper-specific projections are labeled as such. Example 05’s default Gidney–Ekerå path combines compiler-counted logical resources with explicit paper equations. Its --physical path instead performs P3 compilation and scheduling. Neither path simulates or executes the workload.
