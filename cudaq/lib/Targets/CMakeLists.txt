# Declarative target descriptions (<name>/<name>.yml), the source of truth
# for every in-tree CUDA-Q target - analogous to a TableGen .td directory:
# cudaq-target-db-gen (a tablegen-style tool, cudaq/tools/cudaq-target-db-gen)
# reads them and emits C++ tables purposed differently for different
# consumers, exactly like mlir-tblgen's multiple -gen-X backends emit
# different C++ from the same .td source.
#
# cudaq/ needs its own precompiled copy of this data (for cudaq-opt's pass
# pipeline registration and cudaq-target-resolve's nvq++ build-time config
# resolution) but must never depend on runtime/ (see cmake/modules/AddCUDAQ.cmake's
# cudaq_finalize_target_database(), which is the separate, runtime/-owned
# database). Both databases are generated by the same tool, from the same
# source files, into two completely independent linked artifacts - no
# cross-dependency between cudaq/ and runtime/ is created.
#
# The actual generation (cudaq_finalize_builtin_target_database()) is
# invoked from the top-level CMakeLists.txt, not here: it must run after
# every add_target_config() call site (including any CUDAQ_EXTERNAL_PROJECTS
# entry) has been processed, the same timing constraint runtime/'s database
# has - see that function's doc comment in AddCUDAQ.cmake.
